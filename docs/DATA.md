# DATA

Fixture provenance, tile format, band scaling, and the exact procedure for
swapping synthetic pixels for real satellite imagery.

**The headline, stated first: the school names and parcel polygons are REAL. The
pixel values are SYNTHETIC.** Details below, along with why that division exists
and what it does and does not prove.

## 1. What is real and what is not

```
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  ✓ REAL                                                                  │
  │                                                                          │
  │    school names and cities                                               │
  │    parcel polygons          OpenStreetMap, ODbL, retrieved 2026-08-05     │
  │    OSM way IDs              verifiable against osm.org                    │
  │    UTM projection           EPSG:32612, standard Transverse Mercator      │
  │    planar yard areas        shoelace on projected coordinates             │
  │    Portland cost figures    City of Portland Title 11 fee schedule        │
  │    Landsat/Sentinel physics all formulas and calibration constants        │
  ├──────────────────────────────────────────────────────────────────────────┤
  │  ~ DERIVED, LABELLED AS AN APPROXIMATION                                  │
  │                                                                          │
  │    the recess-yard sub-polygon                                           │
  │      a centroid inset of the real parcel, targeting 9,000 m² of open      │
  │      play space, because building footprints are not available offline    │
  ├──────────────────────────────────────────────────────────────────────────┤
  │  ✗ SYNTHETIC                                                             │
  │                                                                          │
  │    every pixel value in every band                                        │
  │      red, NIR, thermal DN, QA                                            │
  │      generated by @canopy/fixtures-synth with a fixed seed                │
  │      calibrated to realistic per-region ground truth                      │
  └──────────────────────────────────────────────────────────────────────────┘
```

### Why this split

Real satellite rasters could not be fetched on the machine this was built on. The
choice was between shipping nothing, shipping something undisclosed, or shipping
something synthetic and saying so loudly. Only the third option is defensible.

Rather than fabricate the whole thing, everything that *could* be real was made
real — the schools exist, the polygons are downloadable from OSM by way ID, the
projection is standard, the physics is published, and the Portland costs come
from a municipal fee schedule.

### How the disclosure is enforced

Not by remembering to mention it. By data:

```ts
// packages/core/src/ports/ImageryPort.ts
export interface SchoolMeta {
  /** True when the fixture's rasters are synthetic. Must surface in the UI. */
  readonly synthetic: boolean;
  /** Provenance note, rendered in the PDF and docs/DATA.md. */
  readonly provenance: string;
}
```

`synthetic: true` drives a persistent badge in the web UI and a line in every
generated PDF and SVG. Removing the disclosure requires editing the fixture
metadata, not the template — and a test asserts it is present:

```ts
expect(report.school.synthetic).toBe(true);
expect(report.school.provenance).toMatch(/OpenStreetMap way \d+/);
expect(report.school.provenance).toMatch(/SYNTHETIC/);
```

### What the synthetic fixtures do and do not prove

```
  ✓ PROVES                                  ✗ DOES NOT PROVE
  ─────────────────────────────────────────────────────────────────────────
  the NDVI formula is implemented right     anything about real Phoenix yards
  the 4-step LST chain is right             any real cooling magnitude
  resampling is genuinely area-weighted     that R² would be 0.73 on real data
  the fit recovers a planted slope          that these schools need trees
  the coverage gate fires at 80%            that 12 trees is the right plan
  the citation gate withholds totals        any real budget figure
  the pipeline is byte-deterministic
  every state renders correctly
  ─────────────────────────────────────────────────────────────────────────
```

The critical design property: **the generator emits reflectance and thermal
digital numbers, never NDVI and never temperature.** The core derives every
displayed quantity exactly as it would from a real scene. A fixture therefore
cannot conceal a bug in the chain, because it never computes any part of it.

### Why the yard is an absolute area, not a parcel fraction

An earlier version took 55% of the parcel, which produced a 30,420 m² "yard" —
an entire campus minus buildings. Yard area is the denominator of canopy
percentage and therefore of `ΔNDVI_yard`, so this scaled the headline temperature
number by roughly 3×.

A recess yard does not scale with the parcel: a 5-hectare campus and a 2-hectare
campus both give children roughly a field plus a hardcourt, and the rest goes to
buildings, bus loop, staff parking and frontage. So the derivation targets an
absolute 9,000 m², capped at 45% of the parcel for small sites.

The figure was chosen to match a typical elementary recess yard, **not** chosen to
make ΔT land anywhere in particular.

## 3. Tile format

Committed as JSON rather than GeoTIFF. A deliberate tradeoff.

```
  fixtures/schools/<slug>/
  ├── meta.json        provenance, grid geometry, MTL constants, ground truth
  ├── yard.json        the polygon, in BOTH WGS84 and projected UTM
  ├── red.json         Sentinel-2 B4 reflectance          200 × 200 @ 10 m
  ├── nir.json         Sentinel-2 B8 reflectance          200 × 200 @ 10 m
  ├── thermal.json     Landsat B10 digital numbers         20 ×  20 @ 100 m
  └── qa.json          Landsat QA_PIXEL bitmask            20 ×  20 @ 100 m
```

### Why JSON and not GeoTIFF

```
  JSON                                    GEOTIFF
  ─────────────────────────────────────────────────────────────────────────
  ✓ no binary assets in the repo          ✗ binary blobs, opaque in review
  ✓ diffable — a changed pixel shows      ✗ any change is an opaque rewrite
  ✓ readable without GDAL                 ✗ needs a geospatial stack
  ✓ Vite inlines it into the bundle,      ✗ needs a fetch or a loader
    which is what makes the demo work
    with the network cable pulled
  ✗ larger on disk                        ✓ compressed
  ✗ not a standard geospatial format      ✓ opens in QGIS
  ─────────────────────────────────────────────────────────────────────────
```

For a fixture whose whole job is to be inspectable and to work offline, JSON
wins. The `ImageryPort` boundary means a real COG reader is an adapter swap, not
a refactor.

### Raster JSON schema

```jsonc
{
  "width":  200,
  "height": 200,
  "data":   [ /* width × height values, row-major */ ]
}
```

Row-major, no nesting, no compression. `NaN` is not representable in JSON, so
no-data is carried by the QA band rather than in the value array.

### meta.json schema

```jsonc
{
  "slug": "cactus-wren",
  "name": "Cactus Wren Elementary School",
  "city": "Phoenix",
  "state": "AZ",
  "synthetic": true,                    // drives the UI badge and PDF line
  "provenance": "Parcel polygon: OpenStreetMap way 121203200 (ODbL), …",
  "osmWayId": 121203200,
  "yardAreaM2": 9000,
  "parcelAreaM2": 55309,
  "yardDerivation": "Recess yard derived as a centroid inset …",
  "ndviCanopyThreshold": 0.66,
  "thresholdRationale": "Raised above the 0.60 default: in irrigated desert …",
  "opticalSceneId": "SYNTH_S2_CACTUS_WREN",
  "opticalDate": "2025-07-30",
  "grid": {
    "epsg": 32612,
    "originX": 393300, "originY": 3716500,
    "finePixelM": 10,  "thermalPixelM": 100,
    "fineSize": 200,   "thermalSize": 20
  },
  "mtl": {                              // per-scene, parsed not hardcoded
    "radianceMult": 0.00038,
    "radianceAdd": 0.1,
    "k1": 799.0284,                     // Landsat 9 Band 10
    "k2": 1329.2405,
    "spacecraft": "LANDSAT_9",
    "acquisitionDate": "2025-07-29",
    "localOverpassTime": "10:42",       // scored honesty label
    "sceneId": "SYNTH_LC09_CACTUS_WREN"
  },
  "groundTruth": {                      // synthetic only — enables validation
    "plantedSlope": -15.4,
    "plantedIntercept": 46.2,
    "targetR2": 0.72,
    "derivedNoiseSdC": 0.31,
    "ndviCellSd": 0.0195,

  }
}
```

`groundTruth` exists only because the fixtures are synthetic. It is what makes
§6's slope-recovery test possible, and it would be absent from a real fixture.

### yard.json

Carries the polygon twice, deliberately:

```jsonc
{
  "type": "Feature",
  "properties": {
    "name": "Cactus Wren Elementary School",
    "osmWayId": 121203200,
    "source": "OpenStreetMap, ODbL",
    "retrieved": "2026-08-05",
    "epsgProjected": 32612,
    "coordinatesProjected": [ [393697.2, 3716002.4], … ]   // UTM metres
  },
  "geometry": {
    "type": "Polygon",
    "coordinates": [ [ [-112.144, 33.574], … ] ]           // WGS84 degrees
  }
}
```

WGS84 for verification against OSM; projected UTM because every geometric
computation — crown radii, yard area, pixel alignment — is metric. Doing that
arithmetic in degrees would make a 7.5 m radius meaningless.

## 4. The synthetic generator

`packages/fixtures-synth`. Seeded, deterministic, and structurally unable to
flatter the pipeline.

### Determinism

```
  mulberry32 PRNG, seeded per school:

  SCHOOL          SEED
  ─────────────────────────────
  cactus-wren     20260805
  john-jacobs     20260806
  sunridge        20260807
  dos-rios        20260808
  ─────────────────────────────
  same seed → byte-identical fixture, asserted by test
  different seed → different pixels, also asserted
```

### The generator emits DN, not derived quantities

This is the property that makes the fixtures worth having.

```
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  GENERATOR EMITS                    CORE DERIVES                         │
  │  ─────────────────────────────────────────────────────────────────────   │
  │  red reflectance         ────────▶  NDVI                                 │
  │  NIR reflectance         ────────▶  canopy classification                │
  │  thermal digital number  ────────▶  radiance → BT → emissivity → LST     │
  │  QA bitmask              ────────▶  cloud mask, coverage ratio           │
  │                                                                          │
  │  The generator computes NONE of the right-hand column. So a fixture       │
  │  cannot hide a bug in the chain that produces it.                         │
  └──────────────────────────────────────────────────────────────────────────┘
```

To emit a thermal DN for a target temperature, the generator runs the physics
**backwards**:

```
      °C  →  LST(K)  →  BT(K)  →  radiance  →  DN

      c   = (λ/ρ)·ln ε
      BT  = LST / (1 − c·LST)              inverse of step 4
      L   = K₁ / (exp(K₂/BT) − 1)          inverse of step 2
      DN  = (L − A_L) / M_L                inverse of step 1
```

If the core's forward chain is correct, feeding it this DN returns the
temperature the generator started from. That round trip is a test.

### Noise σ is derived from a declared R², not hand-tuned

For a linear fit with Gaussian noise, `R² ≈ s²/(s² + σ²)` where
`s = |β₁|·sd(NDVI_cell)`. So:

```
      σ  =  s · sqrt( (1 − R²) / R² )
```

This makes "this fixture fits at R² ≈ 0.72" a *stated property* of the fixture
rather than an accident of tuned constants.

```
  SCHOOL          TARGET R²   REALISED R²   NDVI CELL SD   DERIVED σ °C
  ─────────────────────────────────────────────────────────────────────
  cactus-wren        0.72        0.730          0.0195         0.31
  dos-rios           0.68        0.708          —              —
  john-jacobs        0.63        0.618          —              —
  sunridge           0.55        0.557          —              —
  ─────────────────────────────────────────────────────────────────────
  all within the 0.12 tolerance the test asserts
```

**This is also why fixture R² must never be read as evidence about the real
world.** It was chosen. The thing being validated is that the estimator recovers
what was planted — not that 0.73 is a realistic value for Phoenix.

### Canopy placement uses a quantile cutoff

An earlier version thresholded the crown field directly (`crown < 0.09`), which
produced 0% or 100% canopy and never anything between — summed value noise is
bell-shaped around 0.5, so a raw low cutoff almost never fires.

The cutoff is now the **target quantile of the field's own values inside that
yard**, so the realised canopy fraction matches the target by construction, for
any target:

```
  TARGET   REALISED   SCHOOL
  ─────────────────────────────────
  0.09       9.0%     cactus-wren
  0.12      11.6%     dos-rios
  0.24      24.2%     john-jacobs
  0.55      55.4%     sunridge
  ─────────────────────────────────
```

### Cloud placement is sized in metres

Also a bug fix worth recording. Cloud was originally placed by quantile over the
yard's own thermal cells — but a 9,000 m² yard touches only 1–4 cells, so the
quantile rounded to zero cells and the failure fixture silently stopped failing.

Real cloud is hundreds of metres across regardless of yard size, so the blob is
now metric and offset to occlude *part* of the yard:

```
      radius  =  210 · sqrt(cloudFraction)   metres
      offset  =  0.85 · radius               from the yard centroid
```

At `cloudFraction = 0.34` this yields a 122 m blob, offset 104 m — producing 50%
yard coverage on `dos-rios`. A partial mask is far more convincing than a
blackout and it exercises the coverage ratio rather than just the empty case.

## 5. Band scaling

**The highest-risk bug in any real-imagery ingest.** Level-2 products ship scaled
integers, not reflectance. Applying NDVI to raw DN yields a number in the right
range that is completely wrong.

```
  PRODUCT                          CONVERSION                        VERIFY
  ─────────────────────────────────────────────────────────────────────────
  Landsat C2 L2 optical            reflectance = DN × 2.75e-5 − 0.2   MTL
    SR_B4, SR_B5
  Landsat C2 L2 surface temp       kelvin = DN × 0.00341802 + 149.0   MTL
    ST_B10
  Sentinel-2 L2A                   reflectance = (DN − 1000) / 10000  metadata
    B04, B08                       ⚠ the −1000 BOA offset applies to
                                     processing baseline ≥ 04.00
  ─────────────────────────────────────────────────────────────────────────
```

### The Sentinel-2 offset trap

Baseline 04.00 and later add a BOA offset of −1000. Missing it shifts **every**
NDVI in the scene. Check `PROCESSING_BASELINE` in the product metadata, or read
the `scale` / `offset` fields the STAC item advertises per asset.

### The sanity check that catches all of these

```
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  BEFORE TRUSTING ANY INGEST:                                             │
  │                                                                          │
  │    healthy vegetation  MUST land NDVI 0.4 – 0.8                          │
  │    asphalt / concrete  MUST land NDVI 0.0 – 0.1                          │
  │                                                                          │
  │  If asphalt comes back at 0.45, the scaling is wrong.                     │
  │                                                                          │
  │  ⚠ DO NOT "tune the canopy threshold" to compensate. That is fitting     │
  │    to the answer. Fix the scaling.                                        │
  └──────────────────────────────────────────────────────────────────────────┘
```

### The validation move worth more than the fixture

Landsat Collection 2 Level-2 ships an atmospherically-corrected Surface
Temperature product (`ST_B10`) in the **same STAC item** as the Level-1 radiance.

That means the four-step derivation in [METHOD.md](METHOD.md#4-land-surface-temperature)
has externally-computed ground truth sitting right beside it. Pull both, derive
LST from Level-1, and compare pixel-wise against USGS's own product:

```
  Derived LST vs USGS Level-2 ST  ·  <school>, <date>
    mean absolute difference   _.__ °C
    correlation                _.__
    n                          ____ px
```

Almost nobody validates their own derivation against an independent source. If
agreement is poor, **report it honestly, use the L2 product for display, and keep
the derivation as documented method.** Do not tune the derivation until it
matches — that is fitting to the answer, and one follow-up question exposes it.

This requires network access and is recorded as future work.

## 6. Swapping in real imagery

The `ImageryPort` boundary exists for exactly this. **No model code changes.**

```
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  packages/core          MUST NOT touch the network — compiler-enforced   │
  │  packages/render        MUST NOT                                         │
  │  adapters/*-fixture     MUST NOT                                         │
  │  apps/web               MUST NOT                                         │
  │  ─────────────────────────────────────────────────────────────────────   │
  │  tools/ingest           MAY — it is a build-time tool                    │
  │  adapters/imagery-stac  MAY — the qualifying adapter, gated off          │
  └──────────────────────────────────────────────────────────────────────────┘
```

The offline guarantee is enforced by test, not asserted in prose:

```ts
it('runtime packages contain no network imports or calls', async () => {
  // greps every runtime source file for fetch / axios / node:http / …
  expect(offenders).toEqual([]);
});
it('core declares no runtime dependencies at all', async () => {
  expect(pkg.dependencies ?? {}).toEqual({});
});
```

### Procedure

**Step 1 — find scenes.** Earth Search v1 is anonymous, no key:

```
  STAC API     https://earth-search.aws.element84.com/v1
  collections  sentinel-2-l2a   ·   landsat-c2-l2

  POST /search
  {
    "collections": ["sentinel-2-l2a"],
    "bbox": [lonMin, latMin, lonMax, latMax],
    "datetime": "2025-06-01T00:00:00Z/2025-09-15T00:00:00Z",
    "query": { "eo:cloud_cover": { "lt": 10 } },
    "limit": 20,
    "sortby": [{ "field": "properties.eo:cloud_cover", "direction": "asc" }]
  }
```

Verify asset keys from the first response rather than trusting a list — they
shift between collection versions. Sentinel-2 exposes `red`, `nir`, `scl`;
Landsat exposes `lwir11`, `qa_pixel`, `mtl.json`.

**Step 2 — mind the bucket.** Sentinel-2 COGs on `sentinel-cogs.s3` are openly
readable and answer HTTP range requests with `206 Partial Content`. Landsat
Collection 2 on `usgs-landsat` is **requester-pays**, so anonymous S3 reads fail;
route via `landsatlook.usgs.gov` instead.

**Step 3 — windowed reads only.** `geotiff.js` reads COGs over HTTP range
requests:

```ts
const tiff  = await fromUrl(assetHref);
const image = await tiff.getImage();
const data  = await image.readRasters({ window: [x0, y0, x1, y1] });
```

A schoolyard window is a few hundred KB. A full scene is ~1 GB.

**Step 4 — apply the scaling from §5, then run the asphalt/vegetation check.**

**Step 5 — write the fixture** with real `mtl` constants parsed from the scene's
MTL file, `synthetic: false`, and a provenance string naming the scene IDs.

**Step 6 — pick real yard polygons.** Replace the centroid inset with actual
geometry:

```
  [out:json][timeout:90];
  way(<parcelWayId>);
  (
    way["building"](around:0);
    way["leisure"="pitch"](around:0);
  );
  out geom;
```

Subtract building footprints from the parcel and union the pitches. That removes
the one remaining approximation in the geometry.

### What changes and what does not

```
  CHANGES                              DOES NOT CHANGE
  ─────────────────────────────────────────────────────────────────────────
  fixtures/schools/<slug>/*.json       packages/core          — any file
  meta.synthetic → false               packages/render        — any file
  meta.mtl → real MTL constants        the four gates
  meta.provenance → scene IDs          every test
  groundTruth → removed                the UI
  ─────────────────────────────────────────────────────────────────────────
  the SYNTHETIC badge disappears on its own, because it is driven by
  metadata rather than by a template decision
```

## 7. Cost data provenance

Two regions, deliberately asymmetric. This is the clearest demonstration of the
citation gate.

### Portland, OR — CITED ✓

```
  SOURCE   City of Portland, Portland Parks & Recreation Urban Forestry
           Title 11, Trees Fee Schedule, effective July 1, 2025
  URL      https://www.portland.gov/trees/documents/
           fy-2025-26-trees-fee-schedule/download
  RETRIEVED 2026-08-07
  TIER      2 — city urban forestry program price sheet
```

**Basis.** The City publishes a *Planting and Establishment Fee in Lieu* — what it
charges when a required tree is **not** planted on site. That is the City's own
published valuation of planting and establishing one tree, which is exactly the
quantity needed.

Two published figures, used as the ends of a range with **no interpolation**:

```
  PUBLISHED                          USED AS
  ─────────────────────────────────────────────────────────────────────────
  $712.00 per on-site tree (flat)    LOW end, every class, verbatim
  $472.00 per dbh inch               HIGH end, × caliper
                                       2.0 in → $944.00
                                       1.5 in → $708.00
  ─────────────────────────────────────────────────────────────────────────
```

The 1.5-inch ornamental computes to $708.00, **below** the flat $712.00 the
schedule already states. Rather than push a price under a published number, that
range collapses to $712–$712.

```
  RESULTING LINE ITEMS
  ─────────────────────────────────────────────────────────────────────────
  tree_large_shade_installed        2" caliper     $712 – $944   each
  tree_medium_shade_installed       2" caliper     $712 – $944   each
  tree_small_ornamental_installed   1.5" caliper   $712 – $712   each
  ─────────────────────────────────────────────────────────────────────────

  12-TREE PLAN (6 large + 6 medium)
    low  = $712 × 12 = $ 8,544
    high = $944 × 12 = $11,328
  both ends are arithmetic on published figures
```

**Three limitations recorded in the file itself:**

```
  1  CALIPER IS NOT DBH. Nursery caliper is measured 6 in above ground; dbh
     at 4.5 ft. Close for young 2-inch stock, but the high end is therefore an
     approximation of the schedule's per-dbh-inch basis, not a figure the
     schedule states for caliper.

  2  ESTABLISHMENT IS BUNDLED. The cited fee is "Planting AND Establishment."
     Watering and mulch are already inside it, so perTreeItemKeys is EMPTY for
     Portland. Separate establishment lines would bill the same work twice.
     → this is why Portland shows 2 lines and Maricopa shows 4.

  3  RADII REMAIN UNVERIFIED. Costs are cited; crown radii are not. Separate
     claims, only one resolved.
```

### Maricopa County, AZ — UNCITED ⛔ on purpose

```
  Every price is 0. Every source_name, source_url and source_retrieved is "".

  This is NOT an oversight and MUST NOT be filled in with plausible figures.
```

Its emptiness demonstrates the gate. With both regions present, flipping one
control shows the same plan going from an itemised cited total to a withheld one —
the same code path, two data states. Filling it in would destroy the most
persuasive thing the cost model does.

A test enforces this. If someone "fixes" it by inventing prices, the contrast test
fails and says why.
